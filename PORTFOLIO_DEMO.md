# OpsPilot — портфолио-демонстрация

## Проект в двух предложениях

OpsPilot — учебная operations intelligence-платформа для вымышленного цифрового банка Northstar. Она принимает дневные CSV-агрегаты, проверяет их, рассчитывает KPI, находит всплески нагрузки по понятному правилу и сохраняет управленческий отчёт.

**Бизнес-вопрос:** успевают ли три операционные команды обрабатывать входящий поток и в какие дни стоит проверить необычную нагрузку?

## Сценарий показа — около 3 минут

1. Открой `http://127.0.0.1:5173/`. Интерфейс по умолчанию английский; переключателем **EN / RU** можно показать русский. Укажи, что все данные синтетические.
2. Покажи период, фильтр очереди и пояснения к карточкам KPI. Важное различие: `завершено / поступило` сравнивает два потока за период, а не долю закрытия одной когорты.
3. Выбери период **25–28 августа 2026** и очередь **«Споры по картам»**, нажми **«Показать»**. Объясни сигнал: дневной объём сравнивается с медианой доступных наблюдений предыдущих 28 календарных дней; нужно минимум 14 дней истории; сигнал появляется строго выше 1,5 медианы.
4. Перейди к «Управленческому отчёту» и сформируй сводку. Отчёт использует уже рассчитанные KPI, сохраняется в PostgreSQL и доступен после обновления страницы.
5. При желании открой загрузку CSV: скачай шаблон, проверь файл, затем импортируй. Preview не записывает данные до явного импорта.

На встроенных данных ожидается четыре сигнала по `card_disputes` за 25–28 августа: 88–99 поступлений при пороге около 62. Они показывают всплеск, но не утверждают, что вызвало его.

## Поток данных и инструменты

```text
CSV → Pandas-валидация → FastAPI → SQLAlchemy / PostgreSQL
                                      ├─ KPI и временные ряды
                                      ├─ правило всплеска поступлений
                                      └─ сохранённый шаблонный отчёт
                                           ↓ JSON API
                                      React + TypeScript + Recharts
```

- **FastAPI, Pydantic:** типизированный API, preview/импорт, KPI, сигналы и отчёты.
- **Pandas:** анализ CSV и безопасная проверка табличных строк до записи.
- **SQLAlchemy, Alembic, PostgreSQL:** схема, миграции, транзакционный импорт и сохранение наборов/отчётов.
- **React, TypeScript, Vite, Recharts:** фильтры, карточки KPI, недельные графики и сценарий импорта.
- **Docker Compose:** локальная PostgreSQL с сохранением данных в именованном volume.
- **pytest:** проверки правил расчёта, аномалий, импорта и текста отчёта.

## Бизнес-правила и ограничения

- SLA breach rate = нарушения срока ÷ завершённые кейсы.
- Темп обработки к поступлению = завершённые ÷ поступившие; это сравнение потоков, не когортный показатель.
- Среднее время решения взвешено по числу завершённых кейсов.
- CSAT — невзвешенное среднее дневных оценок: в демонстрационном CSV нет числа ответов на опрос.
- Всплеск поступлений: `today > 1.5 × median(previous 28 calendar days)` при минимум 14 дневных наблюдениях. Метка «сильный» применяется при значении не ниже `2 ×` медианы.
- Сигнал не равен инциденту и не объясняет причинность. Рекомендации и отчётный текст основаны на фиксированных правилах/шаблонах, без LLM.
- Публичный CSV-анализ выполняется без сохранения набора; файл передаётся хостингу для временной обработки. Нет авторизации и live bank integration. Не загружать реальные клиентские или конфиденциальные данные.

## Честная формулировка для резюме

> Разработал OpsPilot — full-stack аналитический MVP для вымышленного цифрового банка: валидация и временный анализ CSV, PostgreSQL-модель, API расчёта операционных KPI, React-дашборд, фильтры, обнаружение всплесков нагрузки и объяснимые рекомендации по правилам. Локальная версия поддерживает импорт проверенного CSV; управленческие отчёты формируются по шаблону.

При желании можно отдельно добавить `AI-assisted development` в описание процесса разработки; не заявлять интеграцию LLM в приложение — её здесь нет.

## Вопросы, которые стоит уметь объяснить

- Почему сравнение завершённых и поступивших кейсов — не процент закрытия одной когорты?
- Почему для SLA используется число завершённых кейсов в знаменателе?
- Почему медиана и 28-дневное окно уместны для учебного правила всплеска, и как проверить ложные срабатывания на новых данных?
- Почему сначала preview, а потом транзакционный импорт?
- Какие поля понадобятся для взвешенного CSAT и когортного времени до решения?
- Что нужно добавить до production: аутентификацию, права доступа, аудит, наблюдаемость, резервное копирование и проверку приватности?

## Перед публичным размещением

Использовать только синтетические данные, добавить тесты вокруг новых форматов CSV и правил, проверить актуальные тарифы хостинга, настроить секреты вне репозитория, базовую авторизацию и резервное копирование. В CV указывать только то, что можешь показать в коде и объяснить на примере.
